# /fund-polish — 润色、提交前自检与交付稿

**规格**：`~/.claude/skills/shared/FUND-PROTOCOL.md`（下称"协议"）。

## 触发场景

章节规划表里各章基本都是"初稿"，要做语言润色、提交前检查，并生成可以交的稿子。

## Step 0：阶段入场

FUND.md 阶段为 `drafting` → 改为 `polishing`。其他阶段不改。

> `drafting → polishing` 只由本 skill 写；`polishing → submitted` 由 `/fund-result submit` 写，本 skill 不写。

## Step 1：读取全文与依据

- `FUND.md`：申请人代码、档案、前序申请、截止日期
- `CLAUDE.md`：交付类型、**`## 申报约束`**（硬限制、官方提纲、表格栏位、排版规范）、限项、章节规划表
- `_profiles/{档案}`：正文结构、匿名要求、合规与限项、评审要点
- `03_正文/` 各章 md
- `07_评审与自检/` 下的真实评审意见（`评审意见_*.md`）和重申修改清单（重申项目）；前序项目的 `07_评审与自检/评审意见_*.md`
- 官方模板与填写说明（`01_官方文件/`）

截止日期在 14 天内时，每次输出第一行提醒剩余天数。

## Step 2：语言润色（调用 `language-polisher-zh` agent）

### 2.0 调用协议（Mode A：Pipeline）

**逐章**调用 `~/.claude/agents/language-polisher-zh.md`：

```
subagent_type: general-purpose
model: opus
（不传 isolation 参数——全局红线）

prompt：
你是中文学术论文润色专家（language-polisher-zh）。Mode A: Pipeline invocation from /fund-polish.

## 输入
- 目标文件：{03_正文/{NN}_{章节名}.md}（完整读取）
- 写作 brief：本项目为中文基金申请书（{基金全称}），非论文、非学位论文
- 评审要点：{档案"评审要点"原文}
- 真实评审意见：{涉及本章的往年意见；没有则写"无"}
- 项目术语表：{从 CLAUDE.md 提取，若存在}
- 字数上限：{CLAUDE.md 章节规划表本章"字数上限"，润色后不得超过}
- 申报约束：{CLAUDE.md `## 申报约束` 第 1 块整表 + 第 2 块本文件各行，原样复制}。小节标题、图片占位、引用键一律不动
- 匿名禁用词：{档案要求匿名时传入；否则写"无"}

## 任务
按 2.1–2.5 五个维度润色本章全文，并遵守基金专属约束：
- 说服力：每段回答"为什么值得资助"；禁止纯描述性陈述
- 评审视角：读者是见过数百份申请书的资深评审专家
- 时态：未完成工作用将来时，已有成果用过去时
- AIGC 规避：避免过度连词、模板句式、空洞论断
- 匿名：不得引入任何禁用词

## 结构保护硬约束
禁止改动 `\cite{}` / `\ref{}` / `\label{}` 命令及其参数。发现引用措辞问题只在响应中报告。Step 2.6 会做前后多重集对比，越界即回退。

## 输出
- 润色后的完整章节文本
- 修改摘要表："原文 → 润色后 → 修改理由"
- AIGC 自检清单
```

**约束**：一次一章，不并行；拿到输出后**不立即写回**，先做 Step 2.6。

### 2.1 学术规范性
- 是否符合申请书文体；有无口语化、冗余、语病
- 避免过度自谦或过度夸大

### 2.2 说服力强化
- 立项依据是否构建了"已知 → 未知 → 本项目填补"的逻辑链
- 意义是否同时覆盖理论和实践，是否扣住档案的选题定位
- 创新点是否锐利，有无"一定程度上""有所创新"等弱化词
- 研究方案是否让评审相信"这个人能做出来"
- 每节首句、末句是否能让快速浏览的评审抓住要点

### 2.3 逻辑连贯性
- 立项依据 → 研究内容 → 技术路线 → 预期成果是否一脉相承
- 段与段之间的过渡、前后有无矛盾

### 2.4 术语一致性
- 同一概念全文同一术语；英文术语首次出现有中文对照；缩写首次出现有全称

### 2.5 数据准确性
- 数字、百分比、年份前后一致；文献信息准确

### 2.6 Token Drift 检查（强制，逐章）

polisher 越界改动 `\cite/\ref/\label` 是静默 bug，必须前后多重集对比兜底。

- 润色前：扫描当前章节全文，得 `{CITE_BEFORE}`（`\cite`/`\citep`/`\citet` 的所有 key，`\cite{a,b}` 展开为独立元素）、`{REF_BEFORE}`（`\ref`/`\autoref`/`\eqref`）、`{LABEL_BEFORE}`（`\label`），按出现顺序保留重复。
- 润色后：对 polisher 输出做同样扫描。
- 计算 `cite/ref/label` 的新增与删除。
- **全部为空** → 静默通过。
- **任一非空** → 输出 Token Drift 报告（列出新增、删除的 key 或 label），AskUserQuestion：[1] 接受全部变化 [2] 回退并重试（强调不得改动 cite/ref/label）[3] 部分接受（用户指明，主 agent 手动合并）。

**严禁**未呈现 Token Drift 就进入下一步。即使 polisher 自称没改引用，也必须做对比。

### 2.7 写回门槛

全局安全红线："严禁未经确认就修改文件"。

1. 逐章展示修改摘要表，不写回任何文件
2. AskUserQuestion：(1) 全部接受本章 → 写回；(2) 逐条审批 → 每条接受、拒绝或改写；(3) 拒绝本章 → 跳过
3. 只有 (1) 或逐条确认后才写回 `03_正文/{NN}_{章节名}.md`；"改写"要再跑一轮 agent 并再过本门槛
4. 多章串行，一次只处理一章

写回后把 CLAUDE.md 章节规划表里本章状态改为 `定稿`。

## Step 3：格式与篇幅检查

### 3.1 篇幅与必答项
运行 `python3 -I "$FUNDINGS/_scripts/check_limits.py" .`，把三张表原样贴进报告：
- 各章字数；
- 官方提纲必答项（缺小节即不通过）；
- 全文硬限制（字数、图片、参考文献、前期成果）。

页数在 Step 7 生成交付稿后用 `--docx` 再核一次。数字一律以脚本为准。

### 3.2 必备章节
以 CLAUDE.md 章节规划表为准，逐行检查 `03_正文/{NN}_{章节名}.md` 存在且有实质内容（非空、非占位注释）。不要在本 skill 里硬编码任何基金的章节清单。

### 3.3 图表
- 分辨率足够；图题在下、表题在上；编号连续；技术路线图清晰
- 交付类型为 `word-macro` 时：图表要先转成图片再插入（教育部等带宏模板的要求）

### 3.4 参考文献
- 格式统一（GB/T 7714 或档案指定格式）；无遗漏引用；自引比例合理
- 对照申报约束第 5 块文献预算：总数、中英篇数（check_limits.py 输出的"引用：中文 / 英文"）、各小节分配；正文引用的每个键都要在 `02_文献/文献池.md` 里，也都要在 bib 里（脚本报"bib 里找不到"即不通过）
- 档案要求"申请人的前期成果不列入参考文献"时，逐条核对

### 3.5 排版
- 以 `## 申报约束` 第 4 块为准，在 Step 7 的交付稿上逐个元素核对（见 Step 7 校验）

## Step 4：合规硬检查（协议第 7 节，提交前必做）

逐条输出"通过 / 不通过 / 无法判断（缺什么）"：

1. **匿名**：档案要求匿名的部分，全文搜索申请人姓名、单位、学校、通讯地址里的地名，以及项目组成员姓名（禁用词来自 `_assets/{代码}/申请人信息卡.md` 和 FUND.md 的项目组成员）。命中即列出章节和原句。另查有无"本课题组""我校"后面紧跟可识别信息的写法。
2. **限项**：按档案"合规与限项"逐条核对，信息来自 `申请人信息卡.md`（职称、在研课题）和 PORTFOLIO.md（同年度其他申报、成员参与次数）。
3. **跨申请人**：运行 `python3 "$FUNDINGS/_scripts/build_portfolio.py"`，读"跨申请人检查"；有题目相近或挂名提示时原样报告。
4. **成果归属**：研究基础、前期成果里的每一项都能在 `_assets/{代码}/成果清单.md` 找到，署名位次一致。

5. **视域落地**：题目有理论视域（选题方案.md"理论框架"不是"无"）时，检查理论词在"内容 / 研究方案"类章节出现，且三处落点（界定、设计、测量）各有对应段落。只出现在题目和意义部分的，判"不通过"，列出缺哪一处。
6. **题目复查**：题目自选题方案以来改过，或 `_library/立项名单/` 有新年度名单时，重跑 `_scripts/title_bench.py`（参数同选题方案记录的对标），比较最近竞争题目和字数分位有无变化，有变化就报告。

"不通过"项必须让用户逐条决定怎么处理，不得自动跳过。

## Step 5：评审视角自检

用严厉评审专家的口径，按档案"评审要点"逐个维度审查全文：

```
### {评审维度}
- 评分：A / B / C / D
- 依据：{引原文，标章节}
- 问题：{具体到段落}
- 修改建议：{具体到句子或给出改写方向}
```

- 档案"评审要点"写"待核"时，用四个通用维度：选题意义、研究内容与方案、创新性、研究基础。
- 有往年真实评审意见的（本项目或前序项目 `07_评审与自检/评审意见_*.md`）：逐条核对本稿是否已回应，列成表"意见 → 本稿对应位置 → 已回应 / 部分回应 / 未回应"。**真实意见的优先级高于模拟评分。**
- 特别检查：研究内容是否只是罗列而没有逻辑；创新点是否空泛；技术路线图和文字是否脱节；立项依据综述是否与自己的工作脱节。
- 末尾给出：最需改进的 3 个方面、亮点。
- 明确说明这是自检，不代表真实评审结果。

报告写入 `07_评审与自检/提交前自检_{YYYY-MM-DD}.md`。用户要求按自检意见修改时，回到对应章节修改（修改同样要过 Step 2.7 的写回门槛）。

## Step 6：跨章节一致性

- 研究内容 ↔ 研究方案：每项内容都有对应方法，每种方法都服务于某项内容
- 创新点 ↔ 立项依据：每个创新点都对应述评里的一条不足，主要不足都被回应
- 经费 ↔ 研究方案（有经费章节时）：设备、差旅、劳务等与方案和团队匹配
- 进度 ↔ 研究内容：覆盖所有内容，时间分配合理
- 预期成果 ↔ 研究内容：成果形式和数量与内容、周期匹配；档案要求"活页与申请书一致"时，两处的预期成果逐项比对

## Step 7：生成交付稿

按 CLAUDE.md 的交付类型生成，写入前 AskUserQuestion 展示预览：

### latex
把 `03_正文/*.md` 正文灌入 `03_正文/main.tex` 对应 `\section{}`，替换 `% 本节正文待灌入自 03_正文/{NN}_{章节名}.md` 占位注释：
- 只灌正文：去掉 `# 章节标题` 和 HTML 注释；`##` → `\subsection{}`，`###` → `\subsubsection{}`
- 转换命令：
  ```bash
  sed -E '/^<!--.*-->$/d; /^# /d' 03_正文/{NN}_{章节名}.md | pandoc -f markdown+raw_tex -t latex
  ```
  `raw_tex` 原样保留 `\...` 命令和 `$...$` 公式
- 章节顺序按章节规划表
- 写入后在 `03_正文/` 里跑 `latexmk -xelatex main.tex` 验证（图片路径靠 main.tex 的 `\graphicspath{{../04_图表/}{../}}` 解析），PDF 复制到 `05_交付稿/`；失败则记录日志并提示排查

### word

**原则**：内容填进官方模板的副本，不另起文档，不改官方模板原件。依据 `## 申报约束` 第 3 块（表格栏位）和第 4 块（排版规范）。

1. **准备副本**：`.doc` 用 `soffice --headless --convert-to docx` 转出，存为 `05_交付稿/{模板名}_填写稿.docx`。系统要求上传 `.doc` 时，最后再转回 `.doc`，并再做一遍校验。
2. **写回填脚本** `scripts/build_deliverable.py`（python-docx；项目已有就沿用），**由主 agent 编写**，规则如下：

   **定位**
   - 按第 3 块的"位置"定位单元格。写入前核对相邻标签格的文字与模板结构文件一致，不一致就停下报错，防止错位写进别的格。

   **结构不动**
   - 不增删行列，不改合并、列宽、行高规则、边框和说明文字。
   - 正文区单元格保留模板的说明段落，删掉模板留的空占位段，正文段落接在说明后面，**仍在同一个单元格里**。
   - 该行若设了"不允许跨页断行"（`cantSplit`）或固定行高（`exact`），会导致内容被截断或出现大片空白。遇到时先报告，经用户同意再改。

   **格式逐段显式设置**（不依赖继承）
   - 每个段落和 run 都按第 4 块写死字体、字号、加粗、行距、段前段后、缩进、对齐。
   - 中文字体必须同时设 `w:eastAsia`。python-docx 的 `font.name` 只改西文字体。
   - 首行缩进用字符单位（`w:firstLineChars="200"`），不用厘米。

   **内容转换**
   - Markdown 的 `##`、`###` 按第 4 块映射到一、二、三级标题。
   - `**…**` 转成加粗 run，其余 Markdown 符号一律去掉。

   **图片**
   - 作为嵌入型图片插入正文区单元格，宽度不超过单元格可用宽度（列宽之和减去单元格边距）。
   - 图片居中，图题放在图下，编号连续。总数不超过硬限制。

   **勾选项**：只把选中的 □ 换成 ☑，保留原有间距。

   **引用**
   - `\cite{}` 按首次出现顺序转成 [n]。
   - 参考文献按 GB/T 7714 列在档案规定的位置。项数不超过硬限制。

3. **三道校验**（全部通过才交给用户）：
   - **结构**：对填写稿重跑 `docx_template_map.py`，与 `01_官方文件/模板结构_*.md` 比对第 1 节（页面）和第 4 节的行、格、跨列、纵向合并、列宽。除"现有文字"外必须完全一致。
   - **计数**：`check_limits.py . --docx 05_交付稿/{…}_填写稿.docx`，核对页数、图片、字数。
   - **目测**：用脚本输出的 PDF，按页渲染成 PNG（PyMuPDF，150 dpi），逐页查看以下问题：
     - 标题层级是否一眼可辨；
     - 有无孤立在页底的标题；
     - 图片是否溢出或过小；
     - 表格边框是否完整；
     - 行距、缩进是否统一；
     - 有无多余空行、空页。

     发现问题就改脚本重跑，不手工改 docx。
4. **提醒用户**：LibreOffice 渲染与 Word、WPS 可能有细微差异（行距、字体回退）。交付前请在 Word 里打开，确认页数和分页。
5. 档案有"活页"和"申请书"两份文件时，分别生成，并在 `05_交付稿/回填清单.md` 里标出两处必须一致的内容（题目、预期成果）。
- 档案有"活页"和"申请书"两份文件时，分别生成，并在回填清单里标出两处必须一致的内容（题目、预期成果）

### word-macro
带宏的官方模板只能在 Windows Word 里填写，不能由脚本生成：
- 生成 `05_交付稿/填报稿.md`：按模板栏目逐栏给出纯文本，标出每栏字数和页数限制
- 图表导出为图片放 `05_交付稿/图/`
- 在填报稿开头写清档案里的操作要求（如：必须用 Windows 版 Microsoft Word、只能保存为 .doc、填完点"检查填报内容并保护文档"）

### system
- 生成 `05_交付稿/系统填报稿.md`：按申报系统栏目逐栏给出纯文本，每栏写"字数 / 上限"，超限的标 ⚠️
- 系统里要上传的附件（如活页 Word）按 word 分支生成
- 账号注册、登录、在系统里填写和提交由申请人本人完成，本 skill 不代填

## Step 8：收尾

- 展示润色摘要、合规检查结果（不通过项置顶）、自检的主要问题、交付稿位置
- 提示："交付稿已生成。提交后运行 `/fund-result submit`，冻结提交版并把阶段改为 submitted。"

## 注意事项

- **润色不是重写**：保持申请人的思路和表达风格，只在规范性和说服力上提升
- **格式以当年官方模板为准**：档案标"待核"的地方，提醒用户核对当年通知
- **说服力 > 华丽**：核心是让评审相信"问题重要、这个人能做、方案可行"
