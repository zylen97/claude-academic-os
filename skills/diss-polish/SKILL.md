# /diss-polish — 学位论文中文润色

## 定位

在 `/diss-draft` 产出中文初稿后，对学位论文逐章进行学术润色。**先审后改、用户确认制**——不擅自改动内容含义，只提升学术表达质量。

---

## 前置条件

- 项目已通过 `/diss-init` 初始化，CLAUDE.md 中有完整章节清单与状态
- `/diss-draft` 已产出至少一章的中文初稿（.tex 文件）
- 中文润色 agent 配置文件存在：`~/.claude/agents/language-polisher-zh.md`

---

## 润色维度

| 维度 | 说明 |
|:-----|:-----|
| **学术规范性** | 使用正式学术中文，消除口语化表达、网络用语、翻译腔 |
| **术语一致性** | 同一英文术语在全文中使用相同的中文译法，不出现一词多译 |
| **逻辑连贯性** | 段落间、小节间过渡自然，论证链条完整，无跳跃或断裂 |
| **语句流畅度** | 句式结构合理，长短句搭配，节奏感好，可读性高 |
| **格式规范** | 引号（中文用""''）、标点（全角）、数字格式（规范使用阿拉伯数字与汉字数字）、专有名词格式统一 |
| **AIGC 规避** | 句长多样化、过渡模式去模板化、段落结构不规则化、学术套话频率控制、结构对称性打破、具体性锚定、词汇丰富度提升——降低 AIGC 检测标记概率 |

---

## 工作流程

### Phase 1：逐章润色（每次处理一章）

#### Step 1 — 读取项目上下文

```
读取项目 CLAUDE.md → 获取：
  - 章节清单与当前状态
  - 已完成初稿的章节列表
  - 术语表（如有）
  - 目标学位论文格式要求
```

**阶段检查**：如果项目阶段仍为 `drafting`，正常执行（允许 draft 和 polish 在章节级别交叉）。仅要求目标章节的初稿已完成。

#### Step 2 — 选择待润色章节

- 向用户展示可润色章节列表（已完成初稿的章节）
- 用户选择本轮要润色的章节（**每次只处理一章**）

#### Step 3 — 自审：问题识别（READ-ONLY）

通读选定章节全文，逐段标记问题。聚焦**内容和结构层面**（语言表达留给 Step 5 的润色 agent）：

- **逻辑问题**：论证跳跃、因果关系不成立、论据不充分
- **术语问题**：同一概念不同译法、术语使用不准确
- **引用格式问题**：`\cite{key}` 被用作句子主语但缺少作者名（顺序编码制下 `\cite{}` 仅渲染为 [N]，需在前面显式写出作者名，如"Barney\cite{key}指出"）
- **冗余问题**：重复表述、啰嗦、信息密度低
- **过渡问题**：段落衔接生硬、缺少过渡句、逻辑连接词缺失

（不包含表达问题和格式问题——这些由 Step 5 润色 agent 处理）

**输出格式**：

```
## 章节 X 自审报告

### 问题汇总（共 N 处）

#### 逻辑问题（M 处）
1. [位置] 具体问题描述 → 建议修改方向
2. ...

#### 术语问题（M 处）
...

#### 冗余问题（M 处）
...

#### 过渡问题（M 处）
...
```

#### Step 4 — 用户确认修改范围

- 向用户展示自审报告
- 用户确认哪些问题需要修复，哪些保留原样
- 用户可补充额外修改意见

**⚠️ 必须等待用户明确确认后才能进入下一步。**

#### Step 5 — 调用润色 agent

##### Step 5.1 — Token 快照（润色前）

调用 polisher 前，对当前章节 .tex 全文扫描并记录三类 token **多重集**（按出现顺序保留重复，捕获同一 key/label 多处使用的情况）：

| 集合 | 来源命令 |
|:-----|:--------|
| `{CITE_BEFORE}` | `\cite{...}` / `\citep{...}` / `\citet{...}` 中的所有 key |
| `{REF_BEFORE}` | `\ref{...}` / `\autoref{...}` / `\eqref{...}` 中的所有 label |
| `{LABEL_BEFORE}` | `\label{...}` 定义的所有 label |

逗号分隔的多 key 引用（如 `\cite{a,b,c}`）展开为独立元素计入。

##### Step 5.2 — 调用 polisher

根据用户确认的修改范围，调用 `language-polisher-zh` agent：

```
调用 ~/.claude/agents/language-polisher-zh.md
输入：
  - 原文（当前章节 .tex 内容）
  - 主 agent 的内容层修复建议（用户已确认的逻辑/术语/冗余/过渡问题修复方向）
  - 语言表达润色指令（口语化/翻译腔、句式/流畅度、标点/格式规范）
  - 反 AIGC 表达多样化指令（句长变异、过渡去模板、段落结构轮换、套话频率控制、对称性打破、具体性锚定、词汇丰富度）
  - 术语表约束
  - **结构保护硬约束**：禁止改动 `\cite{}` / `\ref{}` / `\label{}` 命令及其参数（key/label）；如发现引用相关的措辞问题（如缺少作者主语前缀），仅在响应中报告，不在输出中改动 cite/ref/label 本身
输出：
  - 润色后的完整章节文本（整合内容层 + 语言层修改）
```

##### Step 5.3 — Token Drift 检查（强制）

对 polisher 输出做与 5.1 相同的扫描，得到 `{CITE_AFTER}` / `{REF_AFTER}` / `{LABEL_AFTER}`。

**多重集差异计算**：
- `cite_added` = AFTER 中存在但 BEFORE 中不足的 key（含同一 key 出现次数减少未达 AFTER 数量的差额）
- `cite_removed` = BEFORE 中存在但 AFTER 中不足的 key
- `ref_added` / `ref_removed` / `label_added` / `label_removed` 同理

**判定规则**：

- **全部为空** → 静默通过，直接进入 Step 6（不打扰用户）
- **任一非空** → **强制输出 Token Drift 报告 + AskUserQuestion**（绝不允许静默吸收）：

```
⚠️ Token Drift 报告（润色前后引用/标签结构变化）

\cite{} 变化：
  + 新增（M 处）：key1, key2, ...
  - 删除（N 处）：key3, key4, ...

\ref{} 变化：
  + 新增：...
  - 删除：...

\label{} 变化：
  + 新增：...
  - 删除：...

选项：
  [1] 接受全部变化（确认是合理重写，进入 Step 6 审阅完整 diff）
  [2] 回退并重试（重新调用 polisher，prompt 中再次强调"不得改动 \cite/\ref/\label"）
  [3] 部分接受（用户指明哪些变化保留、哪些恢复原样，主 agent 据此手动合并）
```

**严禁**在未显式呈现 Token Drift 的情况下进入 Step 6。即使 polisher 自称"未改动引用结构"，仍必须执行多重集对比——polisher 越界是**静默 bug**，本步骤为核心原则 5 提供强制执行兜底。

#### Step 6 — 展示修改对比

向用户展示 before/after diff：

- 逐段对比，标注修改类型（术语/表达/逻辑/格式）
- 高亮实质性修改，忽略微调
- 统计修改数量与分布

**⚠️ 必须等待用户逐段审批。用户可接受、拒绝、或要求重改个别段落。**

#### Step 7 — 写入 .tex 文件

- 将用户批准的润色文本写入对应 .tex 文件
- 更新 CLAUDE.md 章节状态为 `polished`

### 阶段转换检查

完成章节润色后，检查项目阶段：
- 读取项目 CLAUDE.md `## 撰写进度` 表中所有章节的状态
- 如果**所有章节状态 ≥ `drafted`**（即 drafted 或 polished，允许 drafting/polishing 章节级交叉），且当前项目阶段仍为 `drafting`：
  → 更新项目阶段为 `polishing`
  → 在 git commit message 中注明阶段转换
- 否则保持当前阶段不变。阶段门槛消歧：
  - `drafting → polishing`：**所有章节初稿（drafted）完成**即触发（不要求任何章节已 polished）
  - Phase 2 跨章一致性检查：**所有章节已 polished** 才触发
  - 单章 polish 不触发阶段转换——"阶段" = 全书状态，"Phase 2" = 全部 polished 后的跨章整合

- Git Checkpoint（里程碑：第 N 章润色完成）：
  > Checkpoint 卡：列出本步精确文件（建议提交信息 `diss-polish: ch{N} polished`），经 AskUserQuestion 单独确认后再执行 focused staging/commit；默认不 push（规格 §5）。

#### 循环 → 回到 Step 2 选择下一章

---

### Phase 2：跨章一致性检查

**触发条件**：当 CLAUDE.md `## 撰写进度` 中所有章节状态均为 `polished` 时，自动进入 Phase 2（全局一致性检查）。

#### 检查项

| 检查项 | 说明 |
|:------|:-----|
| **术语一致性** | 全文扫描：同一英文术语是否始终对应同一中文译法，列出不一致处 |
| **RQ 编号一致性** | 研究问题编号在各章引用中是否一致，无错引、漏引 |
| **章节过渡衔接** | 相邻章节首尾是否自然过渡（上一章结尾 → 下一章开头） |
| **本章小结完整性** | 每章是否都有「本章小结」，内容是否准确概括本章要点 |
| **图表引用一致性** | 图表编号在正文引用中是否正确，无悬空引用 |
| **符号与缩写一致性** | 全文符号、缩写首次出现是否有定义，后续使用是否一致 |

#### 输出

```
## 跨章一致性检查报告

### 术语不一致（N 处）
| 英文术语 | 章节 A 译法 | 章节 B 译法 | 建议统一为 |
|:---------|:-----------|:-----------|:----------|
| ...      | ...        | ...        | ...       |

### RQ 引用问题（N 处）
...

### 章节过渡问题（N 处）
...

### 本章小结问题（N 处）
...
```

向用户展示报告，确认后逐项修复并写入 .tex。

### Git Checkpoint（里程碑：跨章一致性检查完成）

> Checkpoint 卡：列出本步精确文件（建议提交信息 `diss-polish: cross-chapter consistency fixes`），经 AskUserQuestion 单独确认后再执行 focused staging/commit；默认不 push（规格 §5）。

## 核心原则

1. **内容含义不可改变**：润色只改表达方式，不改研究结论、数据、论证逻辑的实质内容
2. **先审后改**：所有修改必须先以报告形式展示，用户确认后才执行
3. **逐章推进**：每次只处理一章，避免大规模并行修改导致失控
4. **术语表优先**：读取 CLAUDE.md 术语表（应在 outline 或 draft 阶段已建立），严格遵循。如发现不一致，报告并建议修正。如术语表不存在，发出警告提示先补建
5. **保留 LaTeX 结构**：润色只改文字内容，不改 LaTeX 命令、标签、引用结构。**该原则由 Step 5.3 Token Drift 检查机制强制执行**——`\cite/\ref/\label` 多重集前后对比，任何变化必须显式报告并由用户决策，绝不静默吸收

## 状态追踪

**统一复用**项目 CLAUDE.md 的 `## 撰写进度` 表（diss-init 创建、diss-draft/diss-polish 共同维护）——不再单独维护独立的"润色进度"表。

状态值推进：`pending → outlined → drafted → polished`（与全局 CLAUDE.md 规范对齐）。

diss-polish 只在该表的"状态"列把章节从 `drafted` 改为 `polished`，并补记日期：

```markdown
| ... | ... | ... | ... | ... |
| 跨章一致性检查 | pending | — | — | — |
```
